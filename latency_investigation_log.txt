--------------------------------------------------------------------------------
 2. SUMMARY OF ROOT CAUSES BEHIND THE LATENCY & BUFFERING
--------------------------------------------------------------------------------
1. Backend N+1 Query Anti-Pattern:
   In `backend/app/services/access.py` (lines 893-911), every ticket serialized makes an individual query:
   `sb.table("escalations").select(...).eq("ticket_id", tid).limit(1).execute()`
   For 22 tickets, this executes 22 separate remote HTTP requests to Supabase in sequence, causing GET /api/v1/tickets to take over 5 seconds.

2. Frontend Sequential Waterfalls in View Ticket Pages:
   In `AssignedTicketDetails.tsx` (lines 220-239), the component awaits `getTicketByIdAsync(id)` first, and only after it resolves does it await `fetchBackendAttachmentsDetailed(id)`. This doubles the perceived loading time from ~1.8s to ~3.5s.

3. Redundant Cache Invalidation & Synchronous Refetches:
   After creating or updating a ticket, the frontend calls `this.clearCache()` followed immediately by `await this.fetchTickets(true)`. Because `fetchTickets(true)` triggers the 5.3-second `/api/v1/tickets` endpoint, the entire UI freezes/buffers until all 22 tickets are reloaded from scratch.

4. Hosting Infrastructure Latency:
   The backend is hosted on Render free tier (`https://ticketing-api-1zjd.onrender.com`), which runs on low-spec container instances and communicates over the public internet to a remote Supabase PostgreSQL database with inherent network latency per round-trip.
